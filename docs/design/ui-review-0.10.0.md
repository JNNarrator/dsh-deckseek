## P1 — 明显问题（阅读时会直接看到）

### P1-1 会话已结束，阅读页第一行却写着「处理中 / In progress」

- **现象**：阅读页最上面是一个「无轮次」的分组（`data-reader-turn="unresolved"`，装的是系统提示、上下文注入、命令记录这些前置记录），它的标题走的是"阶段句"，在一个已经跑完的会话里显示 `In progress`（中文为「处理中」），读起来像还有任务在跑。
- **定位**：`src/client/Reader.tsx` 的 `GroupStatus` —— `turn === null` 时 `kind` 落到 `'none'`，`text` 走 `if (turn?.status !== 'open') return ui('status.process')`。
- **证据**：该分组的按钮 `textContent` 实测为 `"In progressIn progressIn progress"`（可见句 + 量宽占位 + sr-only 活区各一份）；三套皮肤一致。同一个字串还会被 sr-only 活区重复读出。
- **建议**：`turn === null` 时不要渲染状态句（该分组只需要折叠按钮本身）；或另给一句中性文案（如「会话开始前的记录」）。

### P1-2 阅读工具栏（终端皮肤的"窗口标题栏"）不吸顶，会随内容滚走

- **现象**：往下滚一点，工具栏——终端皮肤的窗口标题栏与常驻读数、以及查找 / 动效 / 导出三个按钮——全部滚出视野；终端皮肤的窗口边框顶边也一起滚走，滚到中间时"窗口"这个隐喻就不存在了。
- **定位**：`src/client/Reader.module.css` 的 `.toolbar`（三套皮肤共用）；它没有 `position: sticky`，而 `.searchRow` 有。
- **证据**：`getComputedStyle(toolbar).position === 'static'`；滚动 270px 后，工具栏相对滚动容器的 top = **-270**。三套皮肤一致。
- **建议**：`.toolbar { position: sticky; top: 0; z-index: 2 }` 并补一层背景（否则正文会从下面透出来）；终端皮肤再给一个 `border-bottom` 让它继续像标题栏。

### P1-3 亮色主题下 11–12px 的次要文字对比度不足（3.71:1 < 4.5:1）

- **现象**：亮色（白底）下，四处小字偏淡，实测对比度 **3.71:1**：
  - 收尾读数行（`~22.6k tokens`，11px）
  - 过程元信息行（`Process · 3 tool calls · 1 message`，11px）
  - 终端皮肤的窗口栏读数（`N 轮 · 最新一轮 N 步`，12px，本轮新增）
  - 终端皮肤的窗口栏路径（12px）
- **定位**：这些都取宿主 token `--dsw-alias-label-tertiary`（亮色实测 `rgb(129,133,140)`）。**只在亮色出问题**：暗色下同一 token 是 8.54:1。
- **证据**：白底实测 3.71:1；同页 `label-secondary` 为 12.11:1。
- **建议**：≤12px 的次要文字改用 `label-secondary`，或把这一档字号提到 13px 并按非正文标准（3:1）放宽。**注意 `label-tertiary` 是宿主 token，属于"用错档位"而不是插件配色错**。

### P1-4 悬浮的「回到最新」按钮压住正文一行

- **现象**：滚离底部后，底部中央浮出「回到最新」按钮，它正好盖在正在读的那一行上（三套皮肤、亮暗主题都复现：终端与纸面盖住代码块的一行，软卡盖住一行正文）。
- **定位**：`.jumpDock` / `.jump`（`align-self: center`，浮在阅读区底部中央）。
- **证据**：软卡亮色截图里，`... the single shell comma[按钮]-1:` 被按钮切开。
- **建议**：给滚动内容底部留出与按钮等高的 padding（避免任何一行被压）；或把按钮改成贴右下角、不占正文行。

## P2 — 细节与一致性

### P2-1 终端皮肤：用户回合的文字比回答文字左移 4px

- **现象**：终端皮肤的用户底纹带 `margin: 0 -12px` 出血到窗口内沿，但带内 `padding: 3px 8px` → 文字落在列内容盒左侧 **-4px**，而回答文字在 0，`> ` 提示符与回答左缘不齐。
- **证据**：纸面皮肤同位置实测 band 文字 left = 回答文字 left = 484（对齐）；终端皮肤出血只有这一处，因而只有它错位。
- **建议**：把带的 `padding-left/right` 设为 `var(--dx-frame-pad-x)`（12px），文字即与回答同缘。

### P2-2 终端皮肤：导轨刻度落在窗口边框之外

- **现象**：终端画了窗口边框后，消息导轨的刻度在边框**外** 8px（实测列右缘 1226、导轨 x=1234），读起来像属于"面板"而不是"这个窗口"。
- **建议**：终端皮肤把 `railSpacer` 的右外边距收小（如 `0 4px 0 0`）让刻度贴住边框，或把刻度画进框内。属美术取向，非功能缺陷。

### P2-3 `role="log"` 活区会在词中间断开

- **现象**：屏幕阅读器读到的流式文本会被切成碎片，碎片边界落在单词内部。
- **定位**：`src/client/announce.ts` 的 `splitAnnouncement`（180 字内找不到句界限时按 180 硬切，第 20–22 行），加上增量切片本身就可能停在半个词上；`src/client/Blocks.tsx:93` 用 `join('\n')` 把切片拼进 `role="log"`。
- **证据**：活区文本实测 `"byte-level pass-\nthrough for sam\ne-family proto\ncols and IR-base\nd conversion…"`。**视觉文本是干净的**（同一份文本在 `article` 里的 `textContent` 无杂质、无多余空格），受影响的只是朗读。
- **建议**：180 兜底时回退到最近的空白或词边界再切。

### P2-4 同一屏上"轮数"可能三个口径不一致

- **现象**：实测混合场景（宿主分页把首轮的**用户消息**移出加载窗口后）：窗口栏读数显示 `4+ 轮`，导轨只有 3 个刻度，宿主自己的页脚写 `4 turns`。
- **原因**：读数按"解析出轮号的分组"计数（仍算上首轮），导轨按"有锚点元素的消息"计数（首轮的用户消息不在 DOM 里，故少一个）。
- **建议**：这两个数字同屏出现，含义必须互相对得上——要么读数与导轨用同一口径，要么在读数上说明它是"已加载的轮次"。这是 0.10.0 已修过一轮的同类问题（当时是"所有分组"多算、"以用户消息开头"少算），分页场景下仍需复核。

### P2-5 终端皮肤的空闲屏标识到不了

- **现象**：新建空会话时宿主渲染自己的欢迎页（「Into the Unknown」+ 它自己的输入框），插件的三个页签要有内容才出现——braille 标识只在"阅读页渲染出零轮"时可见（例如只剩不可成组的记录），属边角情形。
- **备注**：机制与契约测试都成立、成本为零，故保留；但"空闲屏一定要有身份"这件事落不到宿主的欢迎页上，需要另议落点（见 [terminal-skin-v4.md](terminal-skin-v4.md)）。

## 已验证正常（同一次复核里排掉的怀疑）

写下来是因为这些是最容易被误报成 bug 的地方：

- **正文/标题/失败卡/用户卡/工具行文字的对比度**：暗色 8.5–17.5:1、亮色 12–18.9:1，全部合格（唯一不合格的是 P1-3 那四处小字）。
- **纸面 0.9.0 的排版阶梯**实测生效：正文 17/30、H2 22/31、表格 16/25、用户消息 15/26、行内码 14.88 —— 正是设计值。
- **软卡 0.9.0 的两处**实测生效：回答卡 `box-shadow` = 宿主 elevation（含 0.5px 描边，亮色下也可分）；用户卡 = 品牌色派生底 + 同色系 0.5px 内描边。
- **终端皮肤 v3/v4 的件**都在跑：状态行呼吸点（`●` 8px、品牌色、`glyphBreathe 1.4s`、容器带 `data-reader-busy=true`）、每轮动词（实测 `Analyzing…` / `Building…`）、折叠计数（`3 tool calls · 2 files · 1 failed`）、收尾行挂右发丝线、用户回合整行底纹带（暗色实测 766px 齐框内沿；亮色为 5% 中性底，在白底上仍可见）、流式光标规则。
- **容器查询**：容器宽 502px 时，窗口栏读数与消息导轨按设计隐藏（480/520/640 三档都对）。
- **插件自身没有横向溢出**：包括出血的用户底纹带在内，没有任何插件容器把父级撑出可滚动宽度。实测唯一溢出的是宿主自己的 `frame` 元素（`overflow-x: hidden`），与插件无关。
- **流式文本的 DOM 是干净的**：`article` 的 `textContent` 无多余空格、无词中插入（P2-3 只影响活区朗读）。

## 测量条件的坑（记录，避免以后误判）

1. **截图在这个面板里不可全信**：复核过程中多次出现"应用被横向推走、右侧一片空白"的截图，而同一时刻 `innerWidth = documentElement.scrollWidth = 1440`、`scrollX = 0`、无 zoom/transform——是面板自身的可视区在两次调用之间变了宽，截图按 1440 出图导致的假象。**结论：判定位置类问题用 `getBoundingClientRect()`，不要用截图。**
2. **宿主在有侧栏展开时会自身溢出**：右侧栏展开（Files 面板或空面板）时，宿主主区左移（实测主区 x = -217、右栏右缘 1592 > 视口 1440），阅读页被推出屏外。这是宿主布局的约束（主区有较大 min-width），**不是插件问题**，但它会污染任何在"侧栏打开"状态下拍的截图——复核时先关侧栏。
3. **`color(srgb …)` 不能按 `rgb(r,g,b)` 解析**：用户卡这类用 `color-mix` 派生出来的颜色，计算值是 `color(srgb 0.86 0.90 0.99)` 形式（0–1 浮点），第一版对比度脚本直接当成 0–255 处理，算出 1.11:1 的假警。**脚本必须先判色彩空间**。
4. **对比度要按元素自己的背景算**：`.railDash` 这种"自身就是一根实心条"的元素没有文字，按文字对比度算必然失败（实测 2.13:1 是假警）。
